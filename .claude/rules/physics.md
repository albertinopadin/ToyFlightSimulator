# Physics and flight model

Moved verbatim from the root `CLAUDE.md` on 2026-09-20 so it loads only when working on the files matched by `paths` above. Keep it current the same way as `CLAUDE.md`.

### Physics (Physics/)
**Composition model**: `GameObject` *has* a `rigidBody: RigidBody?` (it no longer *is* a `PhysicsEntity`). `RigidBody` (class, `World/RigidBody.swift`) implements the `PhysicsEntity` protocol (collisionShape, mass, velocity, acceleration, force, restitution, isStatic, shouldApplyGravity, AABB accessors; identity is `ObjectIdentifier` — no stored id — and `collidedWith` is a `Set<ObjectIdentifier>` reset each step), plus the angular state from Phase D.1: `angularVelocity` and `torque` (world frame; torque is about the body origin, which IS the center of mass — no offset field), `inverseInertiaLocal` (body axes; the zero matrix is infinite inertia, the default for EVERY body, so physics never rotates it and the response's lever-arm terms are exactly zero — `hasFiniteInertia` gates the angular paths; since D.3 an aircraft with a flight model carries `diag(1 / inertia)` from `Aircraft.syncMassProperties`), `inverseInertiaWorld()` = R·I⁻¹·Rᵀ, `stepStartAngularVelocity` (snapshotted next to `stepStartVelocity`), `addForce(_:atWorldPoint:)` (force plus its torque r × F), `velocity(atWorldPoint:)` / `stepStartVelocity(atWorldPoint:)` (v + ω × r), and `rotate(by:)` (world-frame ω·h; composes through a normalised quaternion and rebuilds the matrix so R stays orthonormal for the life of the process — attached bodies rotate their node, detached bodies keep a `standaloneRotation` that `pose()` returns) with `setRotation(_:)` for authoring; it holds a weak back-reference to its GameObject; its initializer self-registers via `gameObject?.rigidBody = self` (the parameter is optional so tests can build Metal-free `RigidBody` doubles — see `TestRigidBody` in PhysicsSolverTests). `BasicRigidBodies.swift`: `SphereRigidBody` (collisionRadius) and `PlaneRigidBody` (collisionNormal, normalized at init so collision response never re-normalizes). `RigidBody.State` is an immutable snapshot (mass, velocity, world axes, rotation matrix) consumed by flight models.

**PhysicsWorld**: entity registry (`addEntity/addEntities/setEntities`) storing concrete `[RigidBody]` — not `[any PhysicsEntity]` — for direct class dispatch in solver loops (see the NOTE in PhysicsWorld.swift if a non-RigidBody entity type is ever added). Runs in UpdateThread. Per `updateType`: `.NaiveEuler` (pair-consuming `EulerSolver.step(...collisionPairs:)`) or `.HeckerVerlet` (HeckerCollisionResponse + VerletSolver); BOTH consume broad-phase candidate pairs, with `useBroadPhase = false` falling back to legacy O(n²) comparison paths. **Force lifecycle** per step: force hooks → apply forces → integrate ω (`AngularIntegration.integrateAngularVelocity`: ω += I⁻¹_world·τ·h, finite-inertia dynamic bodies only) → resolve collisions → integrate/move → integrate orientation (`AngularIntegration.integrateOrientation`: `rotate(by: ω·h)`) → `zeroForces()` (force AND torque). Both solvers order the two angular halves the same way (Box2D/Jolt: velocities, constraints, poses): `EulerSolver.step` runs the ω half right after `applyForces` and the orientation half after `moveObjects`; on the `.HeckerVerlet` path `PhysicsWorld.step` runs the ω half between the force hooks and `resolveCollisions`, and `VerletSolver.step` rotates after its position update. No gyroscopic term. **Solvers**: `PhysicsSolver` protocol (`static func step(deltaTime:gravity:entities:)`); `EulerSolver` (semi-implicit Euler), `VerletSolver` (velocity Verlet — `entity.acceleration` carries a(t) across steps, first step seeded from the forces (`accelerationIsWarm`), `a = F/m + g`). Narrow phase uses squared-distance compares (no pow/sqrt on reject paths). **Collision**: `BroadPhaseCollisionDetector` (X-axis sweep-and-prune; AABBs computed once per entity per frame into reused scratch arrays, index sort on cached min-x keys, stats opt-in via `collectStatistics` — the returned pairs array is reused scratch, consume within the step), `HeckerCollisionResponse` (per pair, contacts from `NarrowPhase.generateContacts`: `correctPosition` — position correction with slop and β at the deepest contact — then the impulses: a single-contact pair — every sphere pair, so every golden — takes `applyImpulse`, an impulse with lever arms at the deepest contact, Hecker's full form, behind a linear fast path for pairs without finite inertia that is the Phase A arithmetic verbatim; a pair with more than one contact is solved by `solveManifold`: eight sequential-impulse iterations (`manifoldIterations`) with accumulated, non-negative impulses and a restitution target captured before the solve (Catto, GDC 2006; one pass left the F-22's two-cap belly rest rocking at 0.029 rad/s, eight rest); `getInverseMassStats` computes the pair's inverse masses AND world inverse-inertia tensors once for both halves). `NarrowPhase.shapeVsPlane` appends into the caller's array (`into:`): a capsule against a plane yields BOTH end caps, deeper first, so a belly-resting fuselage rests on both ends instead of rocking between them; `noteDeepest` keeps the deepest index per appended contact (ties keep the earlier — written against the inout parameter directly, never through a `guard var` shadow).

**Landing gear** (`Physics/Vehicle/`; Steps B.4–B.6 of the compound-rigid-bodies plan): the aircraft stays one rigid body and each gear leg is a raycast spring-damper. `SuspensionStrut` is the per-leg spec — body-local attach point, rest length, travel, and wheel radius in post-import meters (scaled by the body's `uniformScale`, like `LocalCollider`); spring/damping rates and `maxSupportForce` in absolute SI, unscaled (scaling a model does not change its mass). `SuspensionSolver.solve` is the pure per-strut step: compression = reach − raycast distance, capped at `maxTravel`; finite-difference rate against the previous compression (touchdown needs no special case); asymmetric compression/rebound damping; push-only floor at 0; clamp at `maxSupportForce` with `overloaded` judged on the UNCLAMPED value. `LandingGearSuspension` (per aircraft, UpdateThread only) casts each strut's ray along body −up through `PhysicsWorld.raycastStaticPlanes` (nearest static `PlaneRigidBody`, returned as a `RayHit` — distance plus the plane's normal; `NarrowPhase.rayVsPlane` is front-face only, so an inverted aircraft's struts hit nothing), applies the load at the contact patch through `addForce(_:atWorldPoint:)`, and fires `LandingGearEvent`s through `onLandingGearEvent` (`touchdown` with the incoming sink rate and the substep's complete compressions, `liftoff`, per-strut `gearOverload` on the rising edge only); `gearDeployed == false` zeroes compressions and produces no force. `AircraftLandingGearSpec.spec(for:)` is exhaustive over `AircraftType` with no `default` (F-22 CGTrader authored: nose + two mains sharing a 2.05 m reach below the origin; the rest `[]`); `staticStance` gives the equal-reach static compression m·g/Σk and ride height. `PhysicsWorld.standardGravity` (9.81 m/s²) is the one written gravity value; `PhysicsWorld.gravity` is it along −Y. `float3x3.right/up/forward` (MathUtils) name a rotation matrix's basis columns; `float3.up` stays WORLD up. **Wiring (B.5):** `Aircraft.gearSuspension` is installed by `FlightboxWithPhysics.applyAircraftSwap` from `AircraftLandingGearSpec` (nil when the spec is empty, so spec-less aircraft rest on their collision geometry as in Phase A) and stepped from `Aircraft.generateForces` OUTSIDE the input guard — a parked, unfocused aircraft must still be held up — with `isGearDown` as the deploy gate (animator state written only in `doUpdate`, so stable across a frame's substeps). The gear toggle therefore affects physics: the F-22 stands at ≈1.93 m (2.05 m reach − 0.119 m static compression at 30 t) with its fuselage capsule ≈0.88 m clear of the runway, and gear up on the ground drops it onto the fuselage. **Tires (D.2):** `accumulateForces` runs in two passes. Pass 1 is every strut's spring-damper step and its load, applied along the GROUND normal at the contact patch (as Bullet's raycast vehicle applies its suspension impulse), so a pitched or rolled stance pushes nothing along the runway; the compression is still measured along the strut. Pass 2 is `TireModel.solve` (pure, `Physics/Vehicle/TireModel.swift`): holding Coulomb friction over the loaded wheels as sequential impulses (Catto, GDC 2006) against ONE predicted end-of-substep velocity (linear and angular, with this substep's other forces and torques in it) — each wheel in turn applies the impulse that brings its patch's tangent velocity to rest, clamped to the friction circle (rolling resistance 0.02·N along the rolling direction, raised to 0.52·N by a full brake; lateral grip 0.8·N), and updates the prediction; eight sweeps (the first is exact under infinite inertia); no wheel-spin state. At rest that is exactly the force needed and no more, so the parked jet holds at idle on rolling resistance (5.9 kN at 30 t) and against thrust up to the brake capacity (≈137 kN), then slides; a wheel at its limit hands the rest of the demand to the wheels after it (a slip-proportional force creeps at rest; a fixed per-wheel share leaves the unbraked nose's unmet share to nobody). The impulses come back as forces at the patches via `addForce(_:atWorldPoint:)`, so D.3's finite inertia makes them torque-correct with no rewrite. `wheels`/`tireForces` are per-strut scratch on `LandingGearSuspension` (pass 1 rewrites every entry, so nothing carries over). Brakes: `SuspensionStrut.hasBrakes` (defaulted false; the F-22 mains true), `ControlInput.brake` 0…1 from `ContinuousCommand.Brake` (B key held = full; an unfocused aircraft never brakes). Full brakes from 40 m/s stop the jet in about 9 s and 180 m; a 5 m/s crab is gone in 0.65 s. Airframe contacts still carry no friction (gear-up belly slides; D.4). **Steering and the geometric split (D.3):** `SuspensionStrut.maxSteerAngle` (0.35 rad on the F-22 nose gear, 0 on the mains) turns a steered wheel's rolling direction about body up by −steer × range, where `steer` is `ControlInput.yaw` — the same sign as the airborne yaw command, so Q/E turn the nose the same way on the ground; the nose tire's side grip 5.2 m ahead of the origin is the yaw torque (kinematic steering would give 0.48 rad/s at 8 m/s; the mains' side grip and the controller's rate damping hold it to about 0.18, 16.5° of heading in 2 s). With finite inertia the strut loads split by geometry, not spring rate: nose 43 kN / 0.165 m, mains 125 kN / 0.114 m each, a −0.48° nose-down stance (`staticStance`'s level formula, 1.931 m, is still what the overlay logs, 2 mm off). Touchdown settles nose-last, a one-wheel arrival rolls level against the controller, braking dips the nose (+0.145 m nose compression from 40 m/s), and 100 kN against the brakes pivots the origin 4.4 cm forward while the nose dives to −1.80°, then holds — `GearSuspensionWorldTests` carries all of it, with the controller in its rig. The X-key overlay draws each strut as a cyan `Line` from the attach point to the uncompressed contact patch (`ColliderOverlayMapping.strutLineEndpoints`) and logs the static stance; `GearSuspensionWorldTests` is the Metal-free end-to-end settle/touchdown suite. **Classification (B.6):** gear support needs no contact events (the strut compressions carry it); airframe contacts are classified by `AirframeContactClassifier` (pure): approach speed = max(0, −dot(v, n)) along the Contact's B→A normal, `.impact` strictly above `impactSpeedThreshold` (2 m/s), else `.scrape`. The velocity it reads is the relative velocity at the contact point — the aircraft's `stepStartVelocity(atWorldPoint:)` minus the other body's (D.3: a yawing wingtip strikes at ω × r while the origin is still, and a ball thrown at a parked jet closes at its own speed) — from the linear + angular step-start snapshot `PhysicsWorld.step` writes at the top of every substep before any response; `onContact` fires after the pair's impulse, when `velocity` is already the post-impact bounce. `TouchdownReporter` (`Physics/Debug/`, print-only, UpdateThread) prints `[Touchdown]`/`[Liftoff]`/`[GearOverload]` from `onLandingGearEvent` and `[CRASH]`/`[Scrape]` from `onContact` (scrapes throttled 1/s per collider name; impacts once per frame per other body, keyed on `GameTime.TotalGameTime`, so a level belly slap — two cap contacts in one substep — is one line); `applyAircraftSwap` wires both and captures the aircraft weakly (aircraft → rigidBody → onContact → aircraft would cycle). `ContactDebugLogger` stays for general contact cases on other bodies.

**Static structures (Phase C):** `StaticStructure` (GameObjects/) is one box or vertical capsule (`Shape.box(size:)` in full extents, `Shape.capsule(radius:height:)` cap to cap) rendered at its collider's size — the mesh IS the collider, node scale 1, so there is nothing to overlay — with a static `.structure` `RigidBody` it creates in its init (one collider named after the object so contacts name the part, `isStatic`, no gravity, restitution 0.3 so `min()` keeps the aircraft's 0.2 and debris balls stop bouncing, `categoryMask = .structure` with every mask still `.all`); scenes add the body to their world (`FlightboxWithPhysics.addStructure(_:at:)` places the node and appends the body to the entity list; the airfield is an open-front hangar, a control tower, and a tree line, one body per part so contacts name `Hangar_roof`). Box-box (`NarrowPhase.boxVsBox`) is a 15-axis separating-axis test (three face normals each plus nine edge-edge cross products, Ericson §4.4.1) with one contact point, the centroid of the incident face clipped to the reference face (`clippedPoint`: Box2D's manifold reduced to one point); capsule-box (`capsuleVsBox`) is exact — twelve separating axes for a core that touches the box (the box's face normals and the core's cross product with each, both senses), else the least of the two end caps' distances and the core's distance to the twelve box edges. Struts see planes only (`raycastStaticPlanes`); the airframe still collides with roofs and walls.

### Flight Model (Physics/FlightModel/)
**FlightModel** protocol: `computeForce(state: RigidBody.State, input: ControlInput) -> float3` — pure function from rigid-body snapshot + controls to a world-frame force. `ControlInput` (throttle 0–1; pitch/roll/yaw −1…1) flows InputManager → `Aircraft`. A model also authors `mass` and `inertia` (principal moments about the body axes, kg·m², x pitch / y yaw / z roll; the F-22's [390k, 440k, 80k] is scaled from NASA TP-1538's public F-16 data by mass and span²/length², an order-of-magnitude estimate that sets how hard gear and tire torques turn the jet against the controller); torque is not returned (attitude is the rate controller; aerodynamic moments would be the next thing a model returns). Attachment: `Aircraft.flightModel` (optional); `flightModel.didSet` and `rigidBody.didSet` both call `syncMassProperties` (mass + `inverseInertiaLocal = diag(1/inertia)`) so either assignment order converges (duplicate mass field — documented future cleanup in Aircraft.swift).

**F22SimpleFlightModel** sums: engine thrust (`worldForward * maxThrust * throttle`), world-frame lift (AOA from local-frame velocity → Cl via a Catmull-Rom `ValueCurve` spanning −30°…+120°; force perpendicular to wing-plane velocity), induced drag (∝ Cl², ramped in via `SymmetricSigmoidCurve` to suppress it below ~5 m/s), and simple parasitic drag. `LiftData` captures intermediate aero values. Zero-safe `normalize()` from `Float3+Extensions` keeps NaNs out at rest.

**Attitude**: rotation is torque-driven for aircraft with flight physics (a body AND a flight model, `Aircraft.hasFlightPhysics`): `AttitudeRateController` (pure, `Physics/FlightModel/`) turns the stick's rate command into a body-axis torque with the `AttitudeDynamics` time constants — τ = I·(ω_cmd − ω)·(1 − e^(−h/τ))/h per axis, so with no other torque one semi-implicit substep reproduces the old kinematic filter's exact exponential update (flight feels the same; `AttitudeRateControllerTests` pins 0.632 at t = τ) — gear and contact torques add and are damped by the same controller (on the ground it is a rate-damping stability augmentation, not an angle hold: the gear's spring torques still turn the jet to its equilibrium), and `AngularIntegration` rotates the node from inside the step. `Aircraft.generateForces` runs the controller in body axes (Rᵀω in, R·τ out) OUTSIDE the input guard: no focus = zero command = the old decay. Mass and inertia sync from the flight model through `syncMassProperties` on either didSet; removing the model restores infinite inertia and zeroes the angular state. Aircraft without a body or flight model (the F-16 wingman, FreeCamFlightboxScene's jet) keep the kinematic path: the per-axis damped first-order lag filter (rates carried across frames, decay when unfocused; rates snap to 0 below ~1e-4 rad/s so a settled aircraft issues no transform writes) and the A/D side move (`applyPlayerSideMove` is kinematic-only — on the physics path it would slide the jet through its own tire model). See `plans/claude/damped_attitude_response.md`.
